### **1 Project Overview and Scope** 

TaskFlow is a proposed web-based task management system for daily activities. It is intended to help users organize tasks, manage deadlines, set priorities, and monitor progress. The following product goal is a target for the project, not a statement of current capability. 

**Proposed Product Goal.** By 18 December 2026, present a usable web application in which users can register and sign in, manage tasks and deadlines, organize work by category and priority, use a dashboard and calendar, search (required) and filter tasks, and maintain a profile.

### **2 Agile Iteration-Based Mindset and Scrum Framework** 

**Agile** describes values and principles that favor individuals and interactions, working software, customer collaboration, and responding to change. The values do not say that planning or documentation have no value; they prioritize the items on the left of the Manifesto’s comparisons. Frequent delivery and reflection help a team learn and adapt. 3 4 

**Scrum** is a lightweight framework for developing and sustaining products in complex settings. It is not another word for Agile. Scrum defines accountabilities, artifacts, and events that help a team inspect its work and adapt its next steps. A Sprint is a fixedlength period of one month or less, and a new Sprint begins immediately after the prior Sprint concludes. 1 

This project proposes one three-day preparation period followed by four one-week development Sprints. The brief calls the preparation period “Sprint 0” for convenience. It is a common project-planning label, but it is not an official Scrum event or a Scrum Sprint under the Scrum Guide. In this plan it produces decisions and plans, not a software Increment. The four development Sprints have proposed working-software targets. 2 

Scrum events are not interchangeable with ordinary status meetings. Each official event has a defined purpose and creates a formal opportunity to inspect and adapt Scrum artifacts. This regularity also reduces the need for extra meetings. Product Backlog refinement is ongoing work, not a fifth official event. 1

The team proposes using GitHub for shared source work and GitHub Projects as a Kanban board. Members should work in branches, make small commits, open pull requests, review code, and integrate early. The API contract agreed at the end of Sprint 0 is the shared basis for how the frontend and backend exchange data. 

One member may be identified as responsible for coordinating a task, while others pair or review. The Daily Scrum is for Developers to inspect progress toward the Sprint Goal and adapt the near-term plan; it should not become a manager’s status-report meeting. Test a feature against its agreed pass conditions before calling it Done. Never describe intended functionality as already completed. 1 

### **11 Proposed Definition of Done** 

This is a proposed quality checklist for future Increments. The team must agree it and may adapt it as it learns. An item is not Done merely because its code was written. 

1. Acceptance criteria for the item are implemented (including required task search by keyword in the title when applicable). 

2. Code has been reviewed and merged. 

3. The feature works across the frontend, Flask backend, and SQLite where applicable. 

4. Relevant tests pass and the results are recorded. 

5. No known critical bug remains in the item. 

6. The change does not break earlier features. 

7. The interface is consistent and relevant documentation is updated. 

The Scrum Guide defines the Definition of Done as a formal description of the quality state an Increment must meet. This proposed checklist translates that idea into course-project checks; it is not yet a team-approved standard. 1

### **13 Key Scrum Terms Glossary** 

The definitions below summarize the terms used in this proposal. Scrum definitions follow the Scrum Guide. 1 

**_Agile_ – Agile software development** : An approach guided by the Agile Manifesto values and principles, including collaboration, working software, and response to change. 

**_Developers_** : The Scrum Team members committed to creating a usable Increment each Sprint. 

**_DoD_ – Definition of Done** : A shared description of the quality state an Increment must meet to be considered complete in Scrum. **_Increment_** : A concrete, usable, verified step toward the Product Goal that meets the Definition of Done. **_Product Backlog_** : The emergent, ordered list of work needed to improve the product. **_Product Goal_** : The future state of the product that serves as a target for the Scrum Team. **_Product Owner_** : The Scrum accountability responsible for maximizing product value and effective Product Backlog management. **_Scrum_** : A lightweight framework for generating value through adaptive solutions to complex problems. **_Scrum Master_** : The Scrum accountability responsible for establishing Scrum and improving the Scrum Team's effectiveness. **_Sprint Backlog_** : The Sprint Goal, selected Product Backlog items, and actionable plan for delivering the Increment. **_Sprint Goal_** : The single objective for the Sprint that gives the team focus while allowing flexibility in the exact work. **_Sprint 0_** : A project-specific label for the short planning period in this proposal; it is not an official Scrum event or a software Sprint.
